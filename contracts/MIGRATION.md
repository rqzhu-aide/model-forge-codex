# Catalog adoption

## Catalog 1.28.5: useful change accounts and precise observation assumptions

P3 contract 2.11.5 gives the existing summary fields clearer duties: explain the
scientific change or unchanged finding, state what an uncertainty prevents the
researcher from concluding, and keep detailed verification work in its sources.
Assumption explanations distinguish observed measurements from justified bounds
on unobserved outcomes. Short handoffs retain exact references and issue objects.

Shared decision and theory schema descriptions carry these duties into future
writing. Record shapes, scientific conditions, output ownership, question policy
and the shared writing core are unchanged. This adds no word limit or workflow
stage. Existing projects and frozen runs retain their producing catalogs until
explicit adoption; published scientific text is never rewritten by the renderer.

## Catalog 1.4 validation scope

Catalog 1.4 completes the output registry without removing any of the 63
phase outputs. It uses phase-specific object, array-item and JSONL schemas;
adds stable empirical case/replicate links and honest diagnostic
applicability; and checks theory graph references and recorded arithmetic.
The separate assessment response cannot publish or replace theory.

Existing project catalogs do not change merely because the application is
updated. Adoption is an explicit researcher action, refused while runs are
active. Retain the exact old catalog tree in catalog history before adopting
the new tree. A run freezes its catalog at authorization and continues using
that snapshot, even if the project's catalog later changes.

Published scientific bytes, generation IDs and receipts are never rewritten
by adoption. Old generations continue to report their original catalog and
validation scope. They may remain readable through a compatibility view;
missing identities, cases or source links are labeled absent rather than
invented. A new scientific run under 1.4 creates a new validated generation.

`Catalog.version` reports the pin. `manifest_sha256` reports the declared
manifest digest; `snapshot_sha256` computes an actual file-set digest while
excluding the pin and manifest, so metadata timestamps cannot change content
identity. `scientific_validation_enabled` identifies the 1.4+ check scope.
`verify_manifest()` reports missing, changed or unlisted catalog files
without mutating the pin. Refresh the bundled manifest with the shared
Python runtime and `contracts/refresh_manifest.py` after reviewed changes.
Legacy pins retain their historical suffix-based validation behavior; they
are never described as passing the stronger checks.

`output_definitions()` returns the union of declared output records and
stage writes, including legacy cards and diagnostic additions. In 1.4 every
phase output is explicitly registered. `schema_for_output()` returns the
base schema filename; `output_schema()` wraps array-item outputs for complete
document prompts. `validate_output()` accepts a Python array for array-item
and parsed JSONL outputs. `validate_scientific_outputs()` checks collected
output documents and referenced source files against the frozen method.

Arithmetic checks recompute supported summaries from recorded rows. They do
not execute member-authored scripts or establish that the original experiment
was faithfully executed. Source hashes record the submitted script and data;
an original-computation replay, when requested, is a distinct research action.
